# 判据也会写错：一次矩阵实测里，四条方法论各自怎么被验证

这一篇接在《4.41 小时编译之后》之后。上一轮我把「预测错了」拆成四项误差，得到一条结论：**跑前写死的差判据活了下来，绝对判据全错**。这一轮我把同样的纪律用在判据本身，结果发现判据也会写错——而且错了不止一种。

矩阵跑完，13 个合法格全绿、命中率 100%、TTFT 加速 16.5/33.2/51.0 倍。但真正值得记的不是这些数字，是四个「我以为对、其实经不起追问」的瞬间。每一个都对应一条能复用的方法论，我用实测把每条都验证了一遍。

数据来自 `kvmem-study/remote/matrix-sm75/result.json` 与 `kvmem-study/remote/matrix2-sm75/result.json`（两轮各 943 目标零 error，build 4.46 h / 4.83 h）。预注册判据封存在 `kvmem-study/remote/matrix-sm75/PREDICTIONS.md` 与 `kvmem-study/remote/matrix2-sm75/PREDICTIONS.md`，写于开跑前。对账脚本是 `kvmem-study/tools/reconcile_matrix.py`（RED→GREEN 双验）。

## 一、绝对判据和形状判据之间，还有一个「可替换的合法方式」

预注册 D1 写的是「合法格 `returncode` 为正常 terminate」，我在对账脚本里落成了 `rc == -15`（SIGTERM）——因为脚本用 `p.terminate()` 收尾，我想当然地以为进程一定被信号杀掉。

结果第一轮 13 个合法格全报红：`rc = 0`。

第一反应是「引擎没正常退出」。但没急着改判据，先取了一格完整日志（`m-b8192-ctx8192`）：`alive=True`、`ready_after_seconds=22`、两次请求都 200、第二次 `cached_tokens=7279`、日志尾有 `server stopped`。`terminate()` 发 SIGTERM，ninfer-serve 捕到后**优雅关闭**，返回 0——不是异常，是我把「正常结束」错误地绑定成了一种特定信号。

改法不是把 `0` 硬塞进判据，而是问「我要验的到底是什么」：是进程真的跑起来并完成探测。于是 D1 改成 `rc ∈ {0, -15}` **且必须有 `ready_after_seconds`**——两个条件缺一不可。这样无论是优雅退出还是被强杀，只要它确实就绪并跑完探测，就算过；反过来，一个秒退的进程 `rc=0` 但没有 `ready`，照样判红。

这里藏着一个更一般的坑：**绝对判据不只是「数值算错」会失效，「换一种合法方式达成同一结果」也会让它失效**。SIGTERM 达成结束有两种合法出口（优雅 0 / 强杀 -15），只认一种是错的。补法永远是把判据抬到「意图层」——不验信号，验「就绪 + 完成」，再对两个信号都放行。

## 二、两条独立路径逐字相等，才叫真的命中

矩阵里三档 ctx（8192/32768/131072）的命中率都是 100%。这是从 `/stats` 的 `context_cache.hybrid.reused_tokens` 读出来的：7,279 / 29,119 / 58,249。看起来没问题。

但「命中率 100%」有两种可能：真的复用了，或者计数器在自说自话。我拿了另一条完全独立的路径对照——OpenAI 兼容接口的 `usage.cached_tokens`。两次相同请求，第二次的 `cached_tokens` 是 7,279 / 29,119 / 58,249。

逐字相等。

这不是巧合能解释的：一条走内部统计端点（`load_report.cpp:87-118` 把 18 个 counter 汇总成 JSON），一条走 v1/chat 的 usage 字段（OpenAI 客户端读的 token 计数），两条代码路径不同、汇总时点不同。它们相等，才说明「第二次请求命中了第一次的前缀」这件事是真的，而不是某个计数器把 `prompt_tokens` 直接抄进了 `reused_tokens`。

方法论：**单一路径的「完美数字」不可信，尤其当它是 100% 这种整齐值时**。找一条独立路径对表，逐字相等才算验真。这条和上一轮「内部自洽不等于起点对」是同一个道理的两个面——上轮是链条内自洽骗了自己，这轮是单路径完美骗了自己。

TTFT 加速也能这样交叉验：7,279 token 命中省下的 prefill 时间，与实测的 16.5× 加速同量级；三档 ctx 的加速比 16.5/33.2/51.0 随 token 数单调上升，符合「命中越多省得越多」的定性预期。

## 三、Host tier 的监控指标，要标清它挤的是哪个池

v5 容量实测里有个反直觉的发现：开 Host tier 后 `kv_capacity_pages` 从 5299 **升到** 5323（+24 页 = +1,536 token）。24 × 2.00 MiB = 48 MiB，恰好等于「少一个 Device 常驻 StateImage」的尺寸（日志 49.1 MiB）——Host 接走了 state，Device 腾出槽给 KV 页。

这一轮的 H 扫描（host_mib 64→8192）把这件事看得更清楚：`host_used` 在 2048 和 8192 两档完全相同（1,086.4 MiB），`host_block_writes` 也完全相同（455）。**Host tier 在 2 GiB 就饱和了**，再加大不给任何收益。

如果不标池，这个数会被误读成「8192 MiB 的 Host 只用了 1,086 MiB，浪费了 7 GiB」。但真相是：4B 模型的 StateImage 只有 49 MiB、能塞进 Host 的前缀块就那么多，2 GiB 已经装下全部可回收内容。剩下的是**结构性上限**，不是配置不足。

RSS 数据更说明问题：H 扫描的 RSS 从 1,102.7 → 1,550.5 → 3,086.6 → 9,233.9 MiB 单调上升，而 KV 页容量几乎不变。Linux 下 pinned host 内存计入进程的 RSS，但不计 GPU 显存——所以 RSS 涨的 8 GiB 是 Host 侧的 pinned slab，不是显存压力。**把 RSS 当「内存占用」一个数字看，会得出「8192 档吞了 9 GB 内存」的错误结论；标清它挤的是 host pool、且换来了 state 槽的释放，才是正确读法。**

方法论：**任何「用量/占用」指标都要带池名和它换来了什么**。同一个数字在 A 池是浪费、在 B 池是必要代价，取决于它替代了什么。

## 四、自己写的判据错了，和引擎写错了，是同一类处置

第二轮 int8 段 6 个判据全红：exit 1，日志是 help 文本。预注册 D1–D3（页数单调）一个都没验到。

根因三步锁进去：
1. 失败在**解析阶段**（不是引擎跑起来之后）——exit 1 + help 文本是 argparse 风格；
2. 读 `serve_options.cpp:62-77` 的 `parse_kv_dtype`，合法名是 `int8`，不是我写的 `int8_g64`；
3. `int8_g64` 是 `capacity.py` 的**内部名**，我把它当成了 CLI 旗标值。

这是我自己写错脚本，不是引擎行为异常。但处置方式和「引擎判据红了」完全一样：不调阈值、不改判据，先定位是**哪一层错了**。判据红只说明「预期与现实不符」，不说明谁错。定位结果决定动作：引擎错 → 改判据或报 bug；脚本错 → 改脚本，判据原样保留重跑。

所以 v3 的唯一改动是 `int8_g64 → int8`，判据 D1–D6 一字不动。预注册文件里补记 v2 的失败根因，但不挪任何一条判据。**判据的价值恰恰在于它不会为了「让结果变绿」而让步**——否则它就不是判据，是装饰。

## 五、四条方法论收在一起

| 教训 | 判据层 | 验证方式 |
|---|---|---|
| 绝对判据要抬到意图层，放行所有合法达成方式 | D1：`rc∈{0,-15}` 且必须有 `ready` | 单格日志取证：优雅关闭返 0 |
| 完美数字要独立路径逐字对表才算真 | 命中率 100% | `/stats.reused_tokens` ≡ `usage.cached_tokens` |
| 用量指标带池名，标清挤的是哪个池、换来了什么 | H 扫描 host_used / RSS | 2 GiB 饱和、RSS 涨的是 pinned host |
| 判据红了先定位哪层错，脚本错不改判据 | int8 v2→v3 | 三步锁解析阶段 + CLI 合法名 |

它们共同的形状是：**判据、指标、预测都是人写的，都会错**。上一轮证明预测会错（绝对判据死、差判据活），这一轮证明判据本身也会错（把合法出口绑死、单路径自证、指标不标池、脚本错当成引擎错）。唯一不变的防线是「跑前写死 + 事后只定位不改判据 + 独立路径对表」。

代价要一并说：形状判据信息量低——它只能告诉你「复用发生了」，不能告诉你「复用多少」。要拿数字，就得承担算错的风险，并把每一处口径、每一次自我纠错都写下来供事后对账。这四件事做完，报告从 01 写到 21，笔记从 01 写到 04，真正沉淀下来的不是 T4 能跑 27B 这类结论，而是**怎么在没人替你验的情况下，让自己的每个数字都站得住**。
